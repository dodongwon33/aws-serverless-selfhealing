문제 정의

개인이 운영하는 서비스는 장애를 24시간 지켜볼 사람이 없고, 실수 한 번(트래픽 폭주, 잘못된 배포)이 곧바로 청구서 폭탄이나 장시간 장애로 이어진다. 이 프로젝트의 목표는 세 가지다.

  • 보이게 한다 — 로그·메트릭·트레이스로 "무엇이, 어느 버전에서, 왜" 실패했는지 추적
  • 스스로 되돌린다 — 사람의 개입 없이 수 분 안에 마지막 정상 버전으로 복구하고, 같은 결함이 다시 배포되지 않게 막음
  • 예산을 넘지 않는다 — "무료 티어라 괜찮다"가 아니라, 공격·실수 상황에서도 비용 상한이 구조적으로 보장되게 함

자가복구 — 2단 자동 롤백

롤백 기회는 두 번이다. 배포하는 순간에는 CodeDeploy가 트래픽 10%로 새 버전을 5분간 관찰하고, 배포 이후에는 알람이 EventBridge를 거쳐 직접 구현한 remediation 함수를 깨운다.

런타임 remediation 의사결정

1. 필터ALARM 상태가 아니면 무시
2. 위임카나리 진행 중 / 최근 20분 내 실패 → CodeDeploy 소관
3. 중복 방지이미 동결 + live=stable → 추가 조치 없이 알림
4. 대상 결정stable / previous / 수동
5. 실행alias 갱신 → 상태 갱신 → 배포 동결 → 메일
상황버전 상태처리
카나리를 우회한 핫픽스가 장애live=7, stable=5v5로 롤백
검증을 통과한 버전이 운영 중 장애live=stable=5, previous=4v4로 롤백, previous 비움
되돌아갈 버전 없음 (최초 배포)live=stable, previous=none롤백 없이 동결 + "수동 조치 필요" 메일
두 알람(5xx율·Errors) 동시 발생첫 실행이 이미 롤백·동결두 번째 실행은 already_frozen

설계하며 막은 실패 모드

연쇄 롤백

CodeDeploy가 먼저 롤백을 끝낸 뒤 알람 이벤트가 늦게 도착하면 "진행 중 배포 없음"으로 보여, 정상 버전을 한 단계 더 되돌릴 수 있다 → 최근 20분 내 실패·중단 배포도 CodeDeploy 소관으로 판단.

플래핑

롤백 후 같은 알람이 다시 울리면 나쁜 버전으로 되돌아갈 수 있다 → 롤백된 버전을 새 stable로, previous는 비워 되돌아갈 경로를 끊음.

재배포 사고

자동 롤백 직후 다음 push가 같은 결함을 다시 배포 → deploy-freeze로 CI 차단, 원인 수정 후 수동 해제.

저트래픽 카나리

개인 서비스는 평소 요청이 0건이라 카나리 5분 동안 알람이 판단할 데이터가 없다 → 카나리 동안 CI가 합성 트래픽(2rps × 7분) 발생, 알람은 분당 20건 미만이면 0%로 처리해 오탐 방지.

복구를 증명하는 장애 시연

Lambda 버전은 환경변수까지 스냅샷한다는 점을 이용했다. scripts/chaos_bad_release.sh는 FAULT_RATE=0.5인 버전을 발행해 live에 직접 올리고(카나리 우회), 3rps 부하를 건다. 예상 흐름은 다음과 같다.

0분장애 버전 live 반영, 응답의 약 50%가 502
~3분5xx율 알람 ALARM
~3.5분EventBridge → remediation → alias를 stable로
~4분200 응답 복귀, 메일 수신, 배포 동결
구현 상태: 코드와 IaC는 완성됐고 단위 테스트·정적 검증·실제 계정 대상 terraform plan까지 통과했다. 실제 배포와 장애 시연 결과(대시보드 캡처, 복구 시간 측정)는 배포 후 이 섹션에 추가할 예정이다.

CI/CD

워크플로트리거단계

deploy.ymlmain push · 수동테스트 → 배포 동결 확인 → terraform apply → 버전 발행 → CodeDeploy 카나리(합성 트래픽 포함) → 스모크(health + 쓰기/읽기 왕복) → stable 승격

AWS 연결 전(저장소 변수 미등록)에는 배포 job이 자동으로 건너뛰어지고 테스트만 실행된다. 동시 배포는 concurrency로 직렬화했다.

권한 경계로 권한 상승 차단

Terraform 배포 역할은 IAM 역할을 만들 수 있어야 하므로, 그대로 두면 관리자 역할을 만들어 탈취할 수 있다. 배포 역할은 iam:PermissionsBoundary 조건을 만족하는 역할만 /selfheal/ path에 생성할 수 있고, 경계를 제거하거나 bootstrap 역할을 수정할 수 없다.

리소스 스코프

Lambda·DynamoDB·SNS·SSM·CloudWatch·CodeDeploy 권한을 selfheal-* ARN으로 한정했다. API Gateway는 ARN이 랜덤 ID라 리전 단위로 한정했다(알려진 한계).

비밀 정보 관리

알림 메일은 GitHub Secret → TF_VAR로 주입하고 sensitive로 표시해 PR plan 코멘트에 노출되지 않게 했다. API 키는 CI에서 마스킹한다. state 버킷은 버전관리·SSE-S3·퍼블릭 차단·TLS 강제를 적용했다.

SNS를 암호화하지 않은 것은 의도한 선택이다. CloudWatch 알람은 AWS 관리형 키(aws/sns)로 암호화된 토픽에 발행할 수 없고, 고객 관리형 KMS 키는 월 $1로 예산 대비 과하다. 토픽에는 알람 메타데이터만 흐른다.

비용 설계 — "무료 티어"가 아니라 "상한"

2025년 7월 프리티어 개편 이후 기존 계정은 12개월 무료 혜택(API Gateway 등)이 만료됐을 수 있다. 그래서 무료 티어가 전혀 없다고 가정하고, 쿼터 월 5만 건을 전부 소진하는 최악의 경우로 계산했다.

다층 예산 방어 — AWS에는 하드 지출 상한이 없다

① 쿼터사용량 계획 월 5만 건 = 요청 수 자체의 상한 (실질적 비용 상한)
② 조기 경보Budgets $10(계정 전체): 실제 50% · 예측 80% 메일
③ 킬스위치실제 100% → SNS → Lambda → API 스로틀 0 + 배포 동결

킬스위치는 Budget Action(유료 가능)이 아니라 SNS 알림 → Lambda로 구현해 추가 비용이 없다. Budgets 데이터는 수 시간 지연되므로 킬스위치는 마지막 안전망이고, 실질적인 상한은 ①이다.

배운 점 · 다음 단계

  • "무료"는 설계가 아니다. 무료 티어가 아니라 쿼터처럼 구조적인 상한으로 비용을 보장해야 한다.
  • 자동화는 자기 자신과 경합한다. 관리형 롤백과 직접 구현한 롤백, CI가 서로를 되돌리지 않도록 위임·동결 규칙을 명시해야 한다.
  • 설계 문서는 코드로 검증해야 한다. 31건 중 다수는 문서만 읽어서는 보이지 않았고, plan과 테스트에서 드러났다.
  • 다음 단계: CodeDeploy BeforeAllowTraffic 훅으로 새 버전 사전 검증, Trivy/checkov IaC 스캔, Slack 알림, 운영 환경 계정 분리.
